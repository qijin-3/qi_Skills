# UI Copy — 参考图 → design.md

从用户提供的参考图**忠实提取**视觉语言，写成下游 Agent（实现 UI、改样式、生成新屏）可直接执行的 `design.md`。

> **核心信条**：相信参考提供者的品味。图里是什么样就写成什么样，不要按外部审美去改写。

---

## 何时使用

- 用户提到 UI Copy，或贴了 / 附了 UI 及其他视觉参考，要抽出风格规范
- 用户要一份给 Agent 用的 `design.md` / `DESIGN.md` / 设计系统说明
- 用户说按某截图、某竞品、某 Moodboard 的视觉去实现

缺图时：先向用户要参考图（路径、聊天附件、或可访问 URL），再继续。

---

## 输出约定

| 项 | 约定 |
|----|------|
| 文件名 | 默认 `design.md`（用户指定 `DESIGN.md` 则从其） |
| 落盘位置 | 用户指定目录；未指定则写到当前工作区根目录或用户正在讨论的项目根 |
| 正文语言 | **Agent 友好英文**：描述名 + 精确值 + 功能角色；避免营销腔 |
| 对用户的说明 | 可用中文简短确认；**文件本体保持英文语义结构** |
| 结构 | 严格遵循 `references/design-md-template.md` |

开始写文件前，先 Read 该模板。

## 工作流

### 1. 收集输入

- 读取用户给出的**每一张**参考图（用图像可读的 Read / 等价能力；URL 则先取到本地或可分析的形式）
- 记下用户口头补充（品牌色、字体名、暗色模式意图）——口头信息可补图中看不清的部分，但**不得覆盖**图中已清晰可见的事实
- 若只有文字没有图：停止提取，请用户补图

### 2. 多图一致性检查

默认产出**一套** `design.md`。

先快速比对：色板冷暖、圆角语言、字体气质、密度、明暗。

- **一致或接近**：合并为一套系统；在 Source 中列出全部参考
- **差异过大**（例如一套极简浅色 SaaS + 一套赛博霓虹营销页，且用户未说明主从）：**先停下来问用户**——选主参考、拆成两份、或声明「以 A 为准、B 仅作局部」——再写文件
- 不要默默平均成四不像

### 3. 逐层提取（忠实优先）

对可见内容按层记录，再写入模板对应节：

1. **Atmosphere** — 情绪、材质感、明暗、疏密
2. **Color** — 主背景、表面、文本阶、边框、阴影、强调色；尽量给 hex/rgba。采样不准时写 approximate，并在节末注明
3. **Typography** — 识别或描述字体气质、字重层级、字距行高、大小关系；认不出的字体标 `inferred` 并给最接近的公开字体备选
4. **Components** — 只写图中出现的组件；形状、填充、描边、圆角、阴影、状态（若有 hover/active 帧）
5. **Layout** — 栅格/分栏/bento/侧栏、首屏结构、间距节奏、图片处理
6. **Responsive / Motion** — 仅写有证据的；无证据就按模板写明 Not observable，不要编造动效体系

**禁止**：

- 改写图中已可见的风格（如实记录即可）
- 编造图中不存在的颜色、字体、组件或布局
- 把通用设计建议写成该项目的硬性 Banned；§8 只写「怎样会不像这些参考」

### 4. 写 design.md

按 `references/design-md-template.md` 填满各节。

- §8 **Do-Not-Diverge** 必须来自「怎样会不像这些参考」，不是通用反模式清单
- §9 **Open Questions** 只留真正影响实现的不确定性
- 写完后用 Write 落盘，并告诉用户路径

### 5. 向用户交代（短）

用几句话说明：

- 主气质一句话
- 色与字体上最关键的 3–5 个 token
- 多图是否合并、若有过你让用户做的选择
- 哪些是 approximate / inferred

不要把整份 `design.md` 再贴进聊天，除非用户要求。

## 质量标准

一份合格的 `design.md` 应让从未见过原图的实现 Agent 仍能：

1. 选对背景/字色/强调色（含大致 hex）
2. 复现圆角、边框、阴影语言
3. 按同一布局哲学搭新屏，而不是换成另一套流行模板
4. 知道什么改动算「破坏忠实度」

若做不到以上四点，回到参考图补提取，而不是靠空话氛围形容词凑篇幅。
